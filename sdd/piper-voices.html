Detailed report

How does a play click use Piper?

Text equivalent: Piper slots into the existing chain after recordings and before eSpeak. The chain always terminates in sound or a verbatim copy; Piper problems never change what users without the pack see. Download failures (F3) and missing Python (F4) live in the Voices download section, not in playback.

Download flow (Voices section):

  • The runtime and each voice are catalog entries like the offline dictionaries: pinned URL, size, SHA-256 (piper-tts 1.8.0 wheel from PyPI, SHA-256 25b4d3f3… verified in the spike; voices at pinned HF revision 6b9cfaac…, SHA-256s recorded: amy cf9ccdec…, alba 1f9da809…, sharvard 234dc4cf…).
  • The runtime install runs python3 -m venv + pip install piper-tts==1.8.0 inside the app data directory; the package bundles its own espeak-ng phonemisation data, so no system espeak is needed for Piper.
  • Progress reporting reuses the existing dictionary-download progress events; a failed or checksum-mismatched download is never installed (existing installer rules).

Explore an outcome

Success · Piper voice plays

Runtime + language voice installed. ▶ on 🇬🇧 /ˈnɒl.ɪdʒ/ runs venv/bin/python3 -m piper -m en_GB-alba-medium.onnx -f <wav> with the text [[ˈnɒl.ɪdʒ]] on stdin; the WAV bytes (peak-amplitude-guarded) are cached and played. Hover text gains “Piper · en_GB” when a Piper result is used; the natural voice reads the transcription directly.

Success · recording plays

Unchanged from sdd/audio-pronunciation.html: a supplied recording still wins over any voice. F1 exists exactly as today.

F1 · pack not installed

No runtime or no voice for the language: the chain silently uses the eSpeak path from the audio-pronunciation page (mnemonic IPA → headword fallback). No message, no UI change; the Voices section simply shows the download buttons.

F2 · Piper fails

The subprocess errors, times out or returns non-WAV output. The chain falls back to the existing eSpeak path — the user hears the eSpeak voice as today. Piper failures are logged for diagnostics but never surfaced as errors.

F3 · download/install fails

Network error, checksum mismatch or install error in the Voices section: the entry shows a failed state with a retry, mirroring dictionary-download behaviour. Playback continues with eSpeak.

F4 · python3 missing

The startup probe finds no python3 (or venv creation fails, e.g. missing python3-venv on Debian). The runtime row is disabled with copy: “Python 3 is required for natural voices. Install Python 3 and retry.” eSpeak playback is unaffected.

Simulation: nothing is downloaded, installed or played. Each state maps to the response or event that causes it.

Detailed report

Dependencies and ownership

Text equivalent: the Voices section (changed) calls new App methods (changed), which delegate to the new voices service and the extended playback chain. Downloads go through the new pack installer; synthesis through the new Piper adapter. The eSpeak chain, audio cache and download plumbing stay as they are.

Ownership and trust boundaries

  • core owns the VoicePack type, the Voices port (list/download) and the chain order (recording → Piper → eSpeak → copy) — pure logic over ports, IO-free and fake-testable.
  • adapters own all I/O: the pinned catalog (URLs + SHA-256, code-only), the installer (python probe, venv+pip with a runner seam, voice file downloads with checksum and atomic rename) and the Piper synthesiser (subprocess with a runner seam, RIFF + peak-amplitude guard, cache).
  • main (App) owns wiring: ListVoices, DownloadVoicePack, VoiceProgress plus the chain field; no business logic.
  • frontend owns the Voices section states and the Piper hover text; it never receives URLs, only pack descriptors and progress.
  • Trust boundary: downloads are pinned + checksummed at the adapter edge (C1); the IPA passed to Piper is the already-normalised transcription text; Piper output reaches the webview only as a data URI; the runtime is third-party code trusted via the pinned checksum (recorded for the license review).
