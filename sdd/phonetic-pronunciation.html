Text equivalent: accents are shown as country flags (for example 🇺🇸 for General American, 🇬🇧 for Received Pronunciation; a compound label such as “UK, Australia, New Zealand” becomes three flags). A label with no known country, such as Northumbria or Early Modern, stays as text. For a word shown on several cards (offline English has one card per part of speech), the pronunciation line appears only on the first card; the other cards look as they do today. Hovering a flag shows the source’s original label.

How it works: the adapter reads and checks the pronunciation (compact)

Text equivalent: the screen asks the adapter, the adapter reads the existing dictionary source, extracts and checks the pronunciation, and returns the entry with up to three pronunciations. On F1 to F5 it returns the entry without them (dashed line). The full sequence is in the detailed report.

  • Outcome: each result shows its IPA pronunciation under the headword, for example hello → /həˈloʊ/ (the form you gave; the online English source returns it). Spanish shows what Wiktionary gives, for example hola → [ˈola]. No extra network request: the data already arrives with each source.
  • Verified today against real data: all four sources carry pronunciations, but in four different shapes (table below). Offline English offers several accents for hello (/hɛˈloʊ/ US, /həˈləʊ/ UK, and more), so the offline word shows /hɛˈloʊ/, not /həˈloʊ/. The online API returns /həˈləʊ/ and /həˈloʊ/.
  • Failure paths: F1 to F5 all end the same way: definitions still show, only the pronunciation line is missing or shortened. A pronunciation problem never hides a definition or fails a lookup.
  • Decisions to settle (see Open questions): how many pronunciations and which accents to show (Q1), keep the source’s / / or [ ] delimiters (Q2), one line per entry rather than per part of speech (Q3), old cached results (Q4), no audio (Q5), and what to show when there is none (Q6).
  • Out of scope: audio playback, non-IPA systems (enPR, respelling), editing or searching by pronunciation.

A result saved by an earlier version has no pronunciations. It shows as today and gains them when it is next refreshed from the source. No forced refetch.

A word with many accents (hello has six) shows at most three; duplicates are merged. The cap is stated once in the Spec.

The source’s markup changed or cannot be parsed for pronunciation. The lookup still succeeds with definitions only; the failure is not shown to the reader.

Scope and open questions

In scope: IPA text for English and Spanish, from offline, cached and online sources, shown in the result view. Out of scope: audio playback, non-IPA notations (enPR, respelling), searching by pronunciation, translating between accents, new languages.

  1. Q1. How many pronunciations, and which? Recommend: up to 3 per entry, in the source’s own order, with the accent label when the source gives one (offline English). For hello offline that is US, UK, Northumbria; online shows two unlabelled values. Alternatives: first only, or US plus UK only.
  2. Q2. Delimiters. English sources write /…/ (phonemic), Spanish writes […] (phonetic). Recommend: show exactly what the source writes; add slashes only if the source gave none.
  3. Q3. Placement. Offline English repeats the same list in every part-of-speech section. Recommend: one deduplicated line per entry, under the headword. Exception: words such as read (online: two different pronunciations for two entries) get each entry’s own line, because they are already separate entries.
  4. Q4. Old cached results. Recommend: leave them; they pick up pronunciations when they next refresh (up to 365 days), no purge. Alternative: ignore old cache records once so pronunciations appear sooner, at the cost of extra online requests.
  5. Q5. Audio. The online sources include audio links. Recommend: out of scope here; a separate feature.
  6. Q6. Missing pronunciation. Recommend: silent (nothing shown).

If an answer adds a failure path, I will add its ID and walkthrough before asking again.

Contracts and decisions

Contracts
IDContract
C1Data. core.Entry gains an optional ordered list Pronunciations; each item has Text (string), Label (string, may be empty; flags or the source’s text, see C4) and LabelTitle (string, the original source label when Label was replaced; empty otherwise). An entry with none has an empty list. Definitions, sources and headword are unchanged.
C2Validation (F2), applied in the adapter and again when a saved result is read. Trim, collapse inner whitespace; drop the item if Text is empty, longer than 64 characters (runes), or contains <, > or any control character. Label follows the same character rules. The 32-character limit applies to the label as shown, after the flag mapping of C4 (a flag counts as 2 characters); the original text kept in LabelTitle may be up to 128 characters, otherwise the label is not mapped. An invalid label is blanked, the text is kept.
C3Order, merge, cap (F4). Keep source order. Two items with the same Text merge into the first. At most 3 items per entry, after validation and merge.
C4Delimiters and labels (Q2, Q7). Text is kept as the source writes it, including /…/ or […]. If it starts with neither, it is wrapped in /…/. Accent labels become flags (design revision R2): General American and US → 🇺🇸; Received Pronunciation and UK → 🇬🇧; Australia 🇦🇺; New Zealand 🇳🇿; Canada 🇨🇦; Ireland 🇮🇪; South Africa 🇿🇦 (matched case-insensitively after trimming). A label with commas is split at the commas; when every part is known the label becomes the flags in order (for example “UK, Australia, New Zealand” → 🇬🇧🇦🇺🇳🇿), and when any part is unknown the whole label stays as the source writes it (Northumbria, South Asia, Early Modern). Revision R4 (approved): the qualifier words “dialectal” and “obsolete” are ignored when mapping (a label of only qualifier words stays as text; approved in chat: “obsolete” is ignored too); when the mapped flags include both 🇬🇧 and 🇺🇸 the pronunciation is generic and the shown label is empty (and so is LabelTitle). When a label is replaced, the original is kept in LabelTitle. Only IPA values are taken: enPR and other respellings are ignored.
C5Sources. Offline English: IPA-class values in the entry HTML, label from the accent qualifier on the same list item, same values repeated in other part-of-speech entries count once (C3; offline English has one entry per part of speech, so the list is per entry and repeats on each card). Offline Spanish: the IPA-class value of the “pronunciación (AFI)” item. Online English: phonetics[].text values in order, skipping items with no text; the top-level phonetic only if no item has text; labels empty. Online Spanish: the “pronunciación (AFI)” row of the Spanish section only, never rows of other languages (Q8).
C6No extra work. Extraction reuses the HTML or JSON already fetched or parsed for definitions. An online lookup makes the same number of requests as today (one); an offline lookup performs no additional dictionary scan.
C7Cache (F3). The disk record format version stays 1. The new field is optional and omitted when empty. A record without it is read as valid, has no pronunciations and is not refetched early. Values read from disk are validated by C2; an invalid value is dropped, the record is kept.
C8Display. When an entry has pronunciations, one paragraph appears directly under the result title and above the first part of speech: items in order, separated by “ · ”, each prefixed by its label and a space when it has one. Text only (never HTML); when LabelTitle is set it is the hover text of the label. First card only (R2): within one displayed result, a later card with the same headword (case-insensitive) and language whose list (every Text and Label, in order) equals an earlier card’s shows no pronunciation paragraph; a differing list is always shown. The paragraph has an accessible name “Pronunciation” (EN) or “Pronunciación” (ES) following the interface language. No paragraph when the list is empty. Long lines wrap, with no horizontal scroll at 360 px.

Ownership, trust boundary and differences from the design

  • Ownership: core owns the type and every validation rule; adapters only extract raw strings; the view only prints text. No adapter decides length, count or labels.
  • Trust boundary: every source string is untrusted. It is validated in core on extraction and again on cache read; the view renders it as text (Svelte interpolation, never {@html}).
  • Difference 1: offline English entries are one per part of speech, so the same line repeats in each card (wording fix to C3 and S2; behaviour per entry unchanged).
  • Difference 2: the cache keeps a record when only its pronunciations are invalid (design F2 and C7 say values are validated on read; this is how).
  • Test approach: core unit tests from S6 to S8; adapter tests against saved real fixtures (S1 to S5, S9, S11 by asserting no extra request through a counting client); cache round trip with an old record and a new one (S7); frontend component tests (S10); one real-browser check at desktop and 360 px during QA.
  • Migration order: core type, then adapters and cache (parallel, they only need the type), then frontend, then regenerate bindings and build. Nothing to migrate on disk.
