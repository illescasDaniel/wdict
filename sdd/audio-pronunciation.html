Detailed report

How does a play click become sound?

Text equivalent: the click reaches the Go app (step 2), which prefers a recording supplied by the lookup data and otherwise synthesises the IPA with eSpeak-NG (step 3). Audio bytes return as a data URI (step 5) and the webview plays them. A failed recording download exits as F2 and falls back to the voice path; a failed synthesis exits as F4 and retries with the headword. Source data for the recording URLs is the same untrusted provider output the app already validates.

Data now discarded that this feature keeps:

  • English online (Free Dictionary API): phonetics[].audio URLs, currently dropped in onlinePronunciations (internal/adapters/provider.go). Text and audio can pair per item.
  • Spanish online (Wikcionario): the response already contains ext-phonos ▶ audio markers in the pronunciation row (seen in test fixtures); the adapter strips them. The audio file name or URL can be kept alongside the IPA.
  • Offline StarDict entries carry no audio; their play source is always the eSpeak voice.

Explore an outcome

Success · recording plays

🇬🇧 /wɜːd/ has a recording URL from the lookup response. wdict downloads it (bounded, cached on disk by URL hash), returns audio bytes as a data URI, and the webview plays them. Hover text: Recording · Free Dictionary API · CC BY-SA 3.0 or Recording · Wikcionario · CC BY-SA 4.0.

Success · eSpeak voice plays

The item has no recording URL (🇺🇸 /wɝːd/, or 🇨🇦 /wɝːd/). The Go app runs espeak-ng -v en-us -m '<phoneme alphabet="ipa" ph="wɝːd"/>' --stdout, strips the surrounding slashes/brackets first, captures the WAV bytes and plays them in the webview. The accent label drives the voice: 🇬🇧 → en-gb, 🇺🇸 → en-us, 🇦🇺 → en-au, 🇳🇿 → en-nz, 🇨🇦 → en-ca, 🇮🇪 → en-ie, 🇿🇦 → en-za (voice availability verified during the build; a missing accent voice falls back to the language default). Spanish items use es variants. A transcription with no accent label uses the language default: English → en-us (neutral General American, per your review comment), Spanish → es (Castilian, confirmed).

F1 · no playable source at click time

The item has no recording URL and eSpeak-NG is not installed (only possible for non-AppImage installs once bundling is decided, Q4). The play button is always shown; clicking it shows inline copy near the item: “No recording, and eSpeak-NG is not installed. Install eSpeak-NG (or use the AppImage build) to hear this transcription.” Nothing is fetched or run.

F2 · recording fails

The recording download fails, times out or exceeds the size cap. The app falls back to the eSpeak voice for the item's accent. If eSpeak is also unavailable, the F1 copy appears. The button stays for a retry.

F4 · IPA not renderable

eSpeak-NG exits with an error or produces no audible output for an unusual IPA string (for example a transcription containing characters outside its phoneme set). The app retries once with the plain headword ("word") in the same accent voice. If that also fails: “Could not synthesise this pronunciation.”

F5 · recording not decodable

The recording downloaded fine but the webview cannot decode its format (usually mp3, missing GStreamer plugin). Per your review comment, no plugin-install copy: the app falls back to the eSpeak voice for the item's accent. If eSpeak is also unavailable, the F1 copy appears. A short docs note about system codecs stays optional.

Simulation: no audio is played and no process is started. For this fullstack feature, each screen state maps to the response that causes it; commands and bytes are shown as they would occur.

Detailed report

Dependencies and ownership

Text equivalent: the play button (changed) calls the App method (changed), which delegates to the new core playback service; the service uses the new audio fetch/cache adapter and the new eSpeak adapter. The changed provider and Spanish adapters feed the optional AudioURL into the existing data flow; caches, installer and lookup flow are untouched.

Ownership and trust boundaries

  • core owns the fallback chain (C6), accent→voice mapping and copy selection — pure logic, IO via ports; it treats AudioURL as opaque and never fetches itself.
  • adapters own all I/O and validation at the edge: URL validation (validSourceURL) happens before any request; download length-capped; eSpeak input is the sanitised IPA (pronunciation normalisation already rejects markup characters; the adapter strips only the surrounding delimiters).
  • main (App) owns wiring only: constructs the service once at startup with the two adapters, exposes PlayPronunciation; no business logic.
  • frontend owns button states, the audio element, the F5 error-event fallback request and copy display; it never receives raw URLs as linkable data — only the data URI it plays.
  • Trust boundary: provider data (URLs) → validated at the adapter edge; bytes → length-capped, cached, returned as data URI only; subprocess input → sanitised IPA or plain headword.
